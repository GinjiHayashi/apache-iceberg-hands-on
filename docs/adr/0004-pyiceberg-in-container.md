# 0004. PyIceberg はホストではなく Jupyter コンテナで実行する

- 日付: 2026-09-26
- 状態: 採用（要件の「ホストの uv 環境で PyIceberg を使う」を置き換える）

## 背景

Polaris は、テーブルを読み込んだクライアントに S3 のエンドポイントを1つだけ伝える。Spark と PyIceberg はどちらも、自分の設定よりこの値を優先する。コンテナ内から RustFS に届くアドレス（`http://rustfs:9000`）と、ホストから届くアドレス（`http://localhost:9000`）は違うので、ホストの PyIceberg とコンテナ内の Spark の両方に合わせることはできない。

## 検討した選択肢

- Windows の hosts ファイルに `127.0.0.1 rustfs` を追加し、ホストからも `rustfs` という名前で届くようにする — 管理者権限で OS の設定を変える必要がある
- PyIceberg も Jupyter コンテナで実行する — アドレスを `rustfs:9000` に統一でき、問題そのものがなくなる
- Polaris の認証情報の払い出しを無効にする — エンドポイントは引き続き伝えられるため、根本的な解決にならない可能性がある

## 決定

PyIceberg は Jupyter コンテナに uv で追加し、ノートブックから使う。ホストの uv 環境は開発ツール（`nbstripout` など）だけに使う。

## 理由

- 要件の「手軽さ」を優先し、OS の設定を変えずに済ませる
- 「JVM を使わない Python だけのクライアントでも同じテーブルを扱える」という学習の狙いは、コンテナ内で実行しても変わらない

## 影響

- ホストに Python の実行環境を用意しなくても、ハンズオンをすべて実行できる
- Trino は S3 のエンドポイントを自分の設定から読むので、この問題の影響を受けない
